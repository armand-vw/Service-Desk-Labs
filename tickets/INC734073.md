## 1. Issue Description

Remote employee reported that following a password reset, the new password worked for webmail, but his off-premises laptop still required his old password for Windows sign-in.

## 2. Investigation & Triage

- The new password authenticated against cloud/web services (webmail), confirming the Active Directory password change had propagated server-side.
- The Windows lock screen on the remote laptop still demanded the previous password — pointing to **locally stored cached credentials**.
- When off the corporate network, Windows authenticates sign-in against cached credentials in the **SAM/LSASS registry hive**. The password was changed while disconnected from the internal network (or via web self-service), so the domain controller updated Active Directory but the laptop never received the updated **Kerberos/NTLM credential hash** due to missing network line-of-sight to the domain controllers.

---

## 3. Resolution Steps

1. Established a remote support session to endpoint **SD1025** (David Wu) via **Tools → Remote Support**.
2. Verified the endpoint was disconnected from the corporate network, forcing Windows to evaluate cached credentials.
3. Launched the **VPN Client** on SD1025 and established an active tunnel to the **Corporate VPN Gateway** (`vpn.corp.local:443`) using **IKEv2/IPSec**.
4. Confirmed the tunnel state (`Tunnel active - routing traffic through corporate network`), restoring line-of-sight to internal Active Directory domain controllers.
5. Triggered a lock/re-authentication or DC sync check, allowing **LSASS** to validate the new password against Active Directory and overwrite the local cached credential hash.
6. Contacted David Wu via **Team Chat** to confirm Windows sign-in now accepts the updated password.
7. End-user confirmed resolution: *"Yep, it's all working now! Thanks a ton for the quick fix!"*

## 4. Root Cause & KB Notes

**Root Cause:** The laptop was authenticating against stale cached Active Directory credentials because it lacked network line-of-sight to the domain controllers while offsite. The password change updated Active Directory, but the updated credential hash never synchronized to the local LSASS cache. Establishing a VPN tunnel restored line-of-sight and allowed LSASS to validate and overwrite the cached credential.

**KB Article:** KB-1071

**Quick Resolution Checklist:**
1. Connect to the remote user endpoint (SDxxxx) via **Tools → Remote Support**.
2. Log in using the old cached password (or have the user log in using their old password while offline).
3. Open the corporate VPN Client and initiate a connection to the corporate gateway (e.g., `vpn.corp.local:443`).
4. Once the tunnel state updates to **CONNECTED**, lock the Windows workstation (**Win + L** or **Ctrl + Alt + Del → Lock**).
5. Attempt to unlock the machine using the **NEW** password.
6. Active Directory will authenticate the request over the VPN tunnel and automatically refresh the local cached credentials.
